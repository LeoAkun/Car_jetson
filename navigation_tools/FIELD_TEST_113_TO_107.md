# 113 → 107 实地导航流程

本流程用于下次实地测试。现在只做准备，不在车辆上执行。

## 已确认的任务

- 地图：`3b2mus`
- 起点：`113`「2教东门航点」，`x=109.31, y=-46.35, yaw=-1.57`
- 中间点：`106`「北3门点」
- 终点：`107`「1教东门」，`x=122.66, y=-249.50, yaw=-1.57`
- 离线规划结果：`113 → 106 → 107`，图权重 `30.0`
- 两段地图坐标直线长度约 `203.59 m`；实际路径以 Nav2 规划结果和现场障碍物为准。

## 现场启动顺序

### 1. 车辆就位和传感器检查

由驾驶员把车辆停在可控、可通行的位置。若现场条件允许，可停在113附近，但不要求当前车位已经等于航点113：本路线会把113作为第一个 Nav2 目标，车辆定位完成后先导航到113，再经过106到107。确认传感器和底盘驱动已经运行；如果没有运行，先在独立终端启动实车驱动：

```bash
source /opt/ros/humble/setup.bash
source /home/akun/workspace/Car_jetson/real_ws/install/setup.bash
ros2 launch launch_real run.launch.py
```

这一启动文件负责 IMU、速腾雷达、双单线雷达、雷达融合、GNSS、底盘和 `cmd_vel` 转 ECU。现场先检查已有驱动服务和实际工作空间，避免重复启动；Livox 的 launch 在当前源码中已注释。启动导航工具不会代替启动这些驱动。

派单前检查脚本所要求的新鲜传感器数据、底盘速度为零，并确认没有上一次残留的导航任务。脚本本身不调用 `nav2_init_pose`，也不验证 `map→base_link` 定位质量或车辆距113的距离。路线送达管理器后，管理器才自动启动重定位、初始位姿、LIO-SAM和Nav2，并在栈就绪后立即发送第一个目标；当前代码没有在发目标前等待人工确认定位质量。`--start 113` 只指定路线第一个目标，不会把当前位姿直接设成113，也不要求车辆已经到113。GNSS到地图定位仍需监测，因为初始化结果决定车辆如何驶向113。

2026-11-02现场排查发现：`3b2mus` 航点表经纬度高度符合 GCJ-02，GNSS驱动输出原始GPS坐标，CSV使用原始GPS坐标拟合地图。不能直接计算接收机经纬度与航点表经纬度之间的距离来判断车辆是否在113；应使用本地图CSV的 `GpsToMapConverter`，再与航点 `x/y` 比较。该坐标基准判断来自全部10个航点的转换对比，原始MQTT数据未声明基准，不应未经核实就改写航点经纬度。

本次静止车辆的GNSS换算位置距113约37–40米，但这不能单独说明车的真实地图位置，也不能推断自动初始化一定失败。源码中的10米是GNSS地图坐标周围的PSO种子采样方框（每个坐标轴±10米）；每个候选还会调用点云匹配，之后的hill-climb没有同一个±10米裁剪。本次只对同一帧点云手动调用重定位服务24次，没有运行完整的 `nav2_init_pose` 自动流程，因此尚未验证该流程能否得到正确位姿。仍需注意质量门槛：重定位分数为 `1 - inlier_ratio`、范围0到1，而初始化器最终接受条件是 `final_score < 10.0`；管理器只等待 `map→odom` TF和导航栈健康，并不检查匹配质量。下次实车运行需全程监测定位、TF、导航反馈和底盘状态；不能仅凭服务的 `success=true` 判定定位可信。详情见 `navigation_monitoring/runs/2026-11-02_15-56-09_preflight_113_107/LOCALIZATION_DIAGNOSIS.md`。

底盘当前协议源码中 `AUTO_MODE=1`、`PAD_MODE=2`、`WHEEL_MODE=3`；README中的模式编号说明与源码冲突，不能据README把 `drive_mode=1` 判为遥控模式。本次反馈 `drive_mode=1`、`is_autodrive=true`、实际车速为0。

### 2. 启动管理栈、监测器并派单

收到“开始113到107导航”后，先做一次只读预检：温度、内存、已有导航进程、ROS 节点和任务状态。预检通过后执行：

```bash
cd /home/akun/workspace/Car_jetson
TZ=Asia/Shanghai NAV_MONITOR_ENABLE_PROTECTION=1 \
  navigation_tools/start_navigation.sh 107 --start 113 --map 3b2mus
```

脚本的顺序是：先拒绝复用旧监测进程；建立本次 `navigation_monitoring/runs/<时间>/` 目录；source 五个 ROS 工作空间；确认或启动 `multi_map_navigation` 管理栈；启动带温度/内存保护的 `nav_task_monitor.py`；等监测节点写出启动记录和新鲜 IMU、合并激光、底盘数据后，才调用 `dispatch_navigation.py`。监测器未就绪时脚本会退出且不派单。保护默认开启，现场命令仍显式设置 `NAV_MONITOR_ENABLE_PROTECTION=1`。

`--start 113` 是固定起点，不会用 GNSS 自动选最近点；`--map 3b2mus` 防止跨地图同号航点歧义。不得使用 `--force` 覆盖仍在运行的任务。

管理器收到路线后从列表索引0开始。若航点列表为 `[113, 106, 107]`，它先按 `re_localization → nav2_init_pose → 等待 map→odom TF → LIO-SAM → Nav2` 启动定位和导航子栈；栈就绪后才把113发送为第一个 `NavigateToPose` 目标。113成功后才推进到106，再到107；车辆若已经在113目标容差内，Nav2可直接判定首目标完成，否则先驶向113。这里的“先到起点”是先执行路线上的首个导航目标，不是先跳过定位初始化，也不是把GNSS位置改成113。

如果脚本报“已有监测器”，先由执行者核对其PID、任务和输出目录；仅在对应任务已经结束后停止该旧监测器并重试。监测就绪超时没有派单，但可能留下本次管理栈和监测器，需要按实际PID核对后清理。`start_navigation.sh ... --dry-run` 仍会启动管理栈和监测器；纯离线检查必须使用 `dispatch_navigation.py plan`。

## 我会持续核对的状态

派单后不能只看命令返回。以以下证据作为“已接收并开始”的条件：

1. `waypoint_task` 记录的航点编号是 `[113, 106, 107]`。
2. `/robot_state=running` 且 `/robot_status.task_status=1`。
3. 管理器日志依次显示重定位、`map→odom` TF、LIO-SAM、Nav2 就绪。
4. IMU、合并激光、里程计、TF、`/vehicle_status` 持续刷新；`/cmd_vel`、实际车速和自动驾驶标志彼此一致。
5. Nav2 action 状态和反馈持续变化，现场进度按 `113→106→107` 推进；只收到 `/waypoint_list` 不算任务已接受。

监测器约每5秒落盘一次快照，记录任务、进程、传感器频率/新鲜度、速度指令、车辆状态、动作状态、CPU、内存和温度。现场执行时每5至10秒查看新增事件和快照，直到成功或故障后的停车与清理核实完成；航点切换、异常和结束立即汇报，正常运行期间至少每60秒汇报一次。启动脚本返回后仍继续监测。

监测器本身没有当前位姿、航点距离或横向偏差字段，也不自动因传感器失新或无进度而停车。现场需补充查看 `map→base_link` 位姿和 `/navigate_to_pose/_action/feedback`，结合本次任务和目标UUID核对剩余距离、恢复次数及路径偏差；同时查看管理栈和 Nav2 日志。不要把 action 历史列表里的旧 `SUCCEEDED` 当成本次107成功，也不要仅凭 `pgrep` 匹配到进程名字就判定子栈健康。

监测目录由脚本最后打印；关键文件为：

```text
monitor.raw.jsonl       # 事件和周期快照
monitor.log             # 监测器自身输出
management_stack.log    # 管理栈启动输出（本次新启动时）
nav2_*.log              # process_manager 保存的 Nav2 输出
```

温度保护必须保持开启：任务开始后，监测器连续两次读到最高热区不低于 `88°C`，或连续三次可用内存低于 `500 MiB`，会发布零速度、报告故障并请求关闭导航子栈。热区读数缺失不代表温度正常。底盘转换节点当前安装版本还会在 `/cmd_vel` 超过 `0.20 s` 没有更新时输出零速度；现场应核对实际运行节点的参数。发现传感器失新、进程消失、任务无进度、定位/TF 异常、车辆实际速度与指令不符或温度快速上升时，立即停止任务并保留日志，不继续派发新目标。

## 异常时停止

优先通过现有故障链路停止活动任务；管理器会取消目标、发布零速度、进入 `fault` 并清理子栈：

```bash
ros2 topic pub --once /process_manager/fault std_msgs/msg/String \
  "{data: 'field_test_113_to_107: operator_stop'}"
```

操作后仍需核对新鲜的实际车速为零和四个子栈确实退出。若管理器已经失联，不能把故障消息发布成功当成停车成功；应配合现场驾驶员接管/急停，并通过 `/process_manager/shutdown_process` 逐一关闭 `navigation2`、`liosam`、`nav2_init_pose`、`re_localization`。单独取消 Nav2 目标可能留下任务状态空挂，不作为本次完整停止流程。

## 结束判据

只有同时满足以下条件才报告“113到107完成”：

- Nav2 对107目标返回成功；
- `/robot_state=idle` 且 `/robot_status.task_status=0`；
- 新鲜底盘反馈确认实际车速为零，且没有持续非零速度指令；
- 重定位、LIO-SAM、Nav2 子进程均已退出；
- 监测器把 `idle` 终态保持确认至少15秒。

出现 `/process_manager/fault`、`/robot_state=fault`、进程异常退出或监测器保护动作时，按故障结束处理，保存对应 `monitor.raw.jsonl`、管理栈日志和 Nav2 日志。当前导航管理器的单航点 `navigation_timeout=300` 参数没有真正约束动作结果等待，所以“没有报错”不能替代上述终态确认。

## 启动前版本核对

当前 `multi_map_navigation` 和底盘转换节点的安装副本与源码一致；Nav2 的安装副本与仓库源码存在差异。现场预检会记录实际 `ros2 pkg prefix`、launch 文件和参数文件路径，再决定是否需要先重新构建/安装 Nav2；未核对前不假设源码中的最新 Nav2 参数已生效。

2026-10-30核对的差异主要是自定义行为树参数重写和充电目标检查器；本次三个点均为普通点。没有因此重建或替换实车安装版本。
