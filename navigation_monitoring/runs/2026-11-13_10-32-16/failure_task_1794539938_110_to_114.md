# Navigation startup failure: task_1794539938 (110 -> 114)

## Finding

The task was received by `navigation_manager`, but navigation did not reach LIO-SAM or Nav2 startup. The startup chain stopped while waiting for a GPS fix for initial pose estimation.

## Evidence

- `python3_5477_1794539864520.log`: task `task_1794539938` was received with waypoints 110 and 114. `re_localization` and `nav2_init_pose` started successfully. The manager then waited for the `map -> odom` transform.
- `python3_6474_1794539941409.log`: the pose initialization node only reported `等待 GPS 数据...`.
- `python3_5473_1794539864494.log`: status reports before and during the task showed GPS position `(0.000000, 0.000000)`, speed `0.00 km/h`, and battery `0.0%`, consistent with the whole-vehicle sensor/status driver stack not running or not publishing.
- `python3_5477_1794539864520.log`: after `stop_navigation_script: operator_stop`, the manager reported that `map -> odom` never appeared and startup failed. The process manager later reported that neither `navigation2` nor `liosam` had been started.

## Conclusion

The immediate blocker was missing GPS input to initial pose estimation. Without the initial pose, localization did not publish `map -> odom`, so the manager never proceeded to LIO-SAM and Nav2. The MQTT task path worked; this was not a route-planning or obstacle-avoidance failure. The logs provide no evidence that Fast DDS was the cause.

For the next run, start the whole-vehicle sensor/driver launch first and confirm that live GNSS and vehicle status are being published before starting navigation and publishing a task.
