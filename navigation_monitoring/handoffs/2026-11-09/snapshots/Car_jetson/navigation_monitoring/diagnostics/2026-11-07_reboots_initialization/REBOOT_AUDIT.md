# 2026-11-07 整机重启离线审计

本文件只读分析已保存的导航监控、逐秒资源 CSV、wtmp、当前可读的内核/看门狗配置，以及用户授权后以 root 导出的系统日志。已获得四个 boot 的全部已持久化内核 journal、各 boot 最后 1500 行系统 journal、当前 dmesg 和完整 pstore 目录列表；详见 `system_logs/`。所有时间均为北京时间 UTC+8。没有启动车辆、ROS、驱动或回放，没有修改系统或程序。

## 结论

两次早期测试中断确实是整机重新启动，不是仅导航进程退出。后面还发现 16:58:52 的另一次系统启动，用户在本轮最新纠正中明确说明那次是手动关闭，故将该次排除出异常重启范围。前两次的现有证据支持“非正常中断后重新开机”，**不能确定是供电瞬降、主板复位、硬件/固件故障，还是未能落盘的内核故障**。

已保存的资源数据不支持持续 CPU 过热、CPU 长期满载、内存耗尽。两次早期中断前均未观察到 Nav2/MPPI 运行，因此不能把它们归因于 MPPI 路径优化、速度单位换算或导航行驶速度。第一次最后数秒机器人进程数上升，第二次刚启动 LIO-SAM；启动过程与中断时间接近，但不能据此认定最后启动的某个进程造成整机复位。

新增系统证据显示，已保存日志中没有 kernel panic、OOM 杀进程、MCE、软/硬锁死或临界温度关机记录，也没有正常系统关机序列；两处 pstore 均为空。同时发现 `enp2s0` 所在 PCIe 链路持续出现可纠正的 Physical-Layer RxErr。这是需要处理的硬件链路线索，但尚无致命/不可纠正错误或错误恢复失败记录，不能据此确定它造成了两次重启。

## 已查到和无法查到的系统证据

- `last -x -F` 将旧会话标为 `crash`，这些断点未见对应的正常 `shutdown system down` 条目。用户级 journal 也突然结束，未保存正常关机收尾。这支持非正常中断，但日志缺失或人工断电同样会产生类似记录；本轮用户确认的人工关机就是具体例子，不能仅凭 `crash` 标签断定异常或硬件原因。
- 最初受账号权限限制只能读取用户日志；本轮用户在桌面授权 sudo 后，已取得 root 导出的系统/内核日志，原权限缺口已解除。两次异常 boot 的全部已持久化内核日志和系统末尾均未发现 panic/OOM/MCE/锁死/温度关机或正常系统关机序列。这里的“未发现”有范围限制：日志最后落盘时间仍早于独立 CSV，不能排除最后未落盘时间段发生故障。
- 第一 boot 的内核及系统末尾均为 **16:14:41.023347**，比 CSV 最后存活记录早 **25.950 秒**。第二 boot 的内核末尾为 **16:17:55.835807**，系统末尾为 **16:17:59.994912**，分别比最后 CSV 早 **33.023 秒、28.864 秒**。不能把 journal 截止时间等同复位时刻。
