### 2026-10-26 内核日志结论

用户提供的插拔日志已经定位根因：

```text
16:08:18 cp210x converter detected
16:08:18 cp210x converter now attached to ttyUSB2
16:08:26 usbfs: interface 0 claimed by cp210x while 'brltty' sets config #1
16:08:26 cp210x converter now disconnected from ttyUSB2
```

这证明本次插入时 CP2102 已被内核 `cp210x` 驱动成功识别，串口最初已经创建为 `/dev/ttyUSB2`。8 秒后 `brltty`（盲文设备服务）重新配置同一 USB 接口，导致 `cp210x` 断开。当前这次串口消失的直接原因已确认为服务冲突；尚不能据此声称 IMU 数据或所有硬件均通过验收。

已准备 `repair-imu-usb.bash`：先核对物理路径 `1-5` 的 VID/PID/序列号，再以运行时 mask 停止两项 brltty 服务，仅给该 IMU 接口重新绑定 `cp210x`，等待 15 秒核对驱动和稳定路径。它不打开串口、不启动 ROS、不修改 udev，运行时 mask 重启后消失。脚本还提供无需 root 的 `--check` 模式。

这一步需要管理员权限；尚未执行系统修改。用户可执行 `sudo bash /home/akun/car-host-step9.MgehLL/repair-imu-usb.bash` 并保存输出，验证通过后再决定如何持久化排除冲突和单独验收 IMU 数据。

同一日志还报告 `enp2s0` 的 r8169 发送超时及 PCIe AER Correctable 错误，属于后续有线网络验收待查项，尚未建立其与 IMU 冲突的因果关系；本轮不调整网卡或内核参数。

### 2026-10-26 永久禁用 brltty（已完成）

用户明确要求永久禁用盲文设备服务。`repair-imu-usb.bash --permanent` 已通过语法和只读预检，执行时在 `/etc/systemd/system/` 为 `brltty.service`、`brltty-udev.service` 创建指向 `/dev/null` 的永久 mask，并立即停止服务，阻止开机和 USB udev 再次拉起。软件包保留，未卸载。

永久禁用可通过 `sudo systemctl unmask brltty-udev.service brltty.service` 撤销；若以前还设置过运行时 mask，另需执行同名 `unmask --runtime`，再按需启动服务。

## 六道门槛

### 0. 断电与机械安全

1. 车辆置于驻车/急停状态，驱动轮离地或有可靠止动；测试人员确认可以立即断电。
2. 记录电池、急停、底盘电源和主机电源状态；不绕过急停，不在车轮可自由转动时测试任何动力节点。
3. 保留 `/home/akun/start_robot_service.sh` 的保护：没有 `ROBOT_HARDWARE_COMMISSIONED=1` 时不能整车启动。

通过条件：机械风险被现场负责人确认，且仍未启动总 launch。

### 1. 设备归属与串口确认

1. 在断电/不打开串口的情况下记录 `lsusb`、`udevadm info`、USB 物理端口、线缆标签和照片。
2. 逐个确认 CP2102 IMU、CH340 设备分别连接到什么控制器；若设备数量不匹配，先检查 USB 集线器、供电和线缆。
3. 只有确认设备序列号/USB 路径后，才建立持久化 udev 名称。不得把 `/dev/ttyUSB0` 当作固定设备名，也不得给重复 CH340 创造相同 by-id 别名。
4. 先对 IMU 做只读/不发控制的串口握手，确认波特率 921600、帧率和错误计数；失败即停止，不尝试其他未知波特率向设备写入。

通过条件：IMU 对应的持久化路径真实存在，串口权限为 `akun:dialout`，且能连续得到有效 IMU 数据；否则不能进入传感器综合测试。

### 2. 网络与雷达确认

1. 先用交换机/线缆标签确认专用传感器网段。不得把 Livox 的 `192.168.1.x` 配置直接改到当前 Wi-Fi 网段，也不得修改默认路由来“试通”。
2. 需要改地址时，只给明确的有线接口配置临时静态地址；保留 Wi-Fi `192.168.3.23`，不修改 netplan 和办公网络。
3. 先单独确认 Livox UDP 端口 56100/56200/56300/56400，随后确认 RS LiDAR UDP 6699/7788，再确认前后单线雷达 2368/2369。每项只观察数据包和 ROS 话题，不同时启动多个同端口驱动。
4. 网络测试使用抓包/端口监听和驱动日志；不对未知地址发送配置或重启命令。

通过条件：有线接口地址、雷达地址、端口和接口绑定均有记录，且单独启动各雷达时能稳定输出点云/扫描，不影响 Wi-Fi。

### 3. 传感器单项启动

按顺序单独启动并限时记录 30--60 秒：

1. IMU：只启动 `ahrs_driver_node`，验证 `/imu` 频率、`imu_link`、时间戳和异常重连。
2. RS LiDAR：只启动 `rslidar_sdk`，验证 `/rslidar_Pointcloud2` 的字段、`ring`、`time`、点数和 `rslidar` frame。
3. Livox：只启动 MID360 驱动和 `convert_laser`，验证 `/livox/lidar` 到 `/livox_Pointcloud2`，不启动 LIO-SAM。
4. 前后单线雷达：分别验证 `laser/scan_front`、`laser/scan_back` 和 frame；再启动融合器确认输出。
5. 相机最后验证，只做设备枚举/帧率和图像话题检查；坑洼检测默认关闭，不在此阶段启用。

每次结束都只停止本次启动的进程，并确认没有残留节点、串口占用或 UDP 监听。

### 4. 无动力控制链

1. 只启动 `command_mux` 和 `cmdvel_2_ecu`，将 ECU 输出重映射到测试话题；不启动 `chassis_driver`、USB-CAN、锁控制或整车 launch。
2. 验证无输入、输入超时、泊车独占、释放泊车和急停路径都输出零速/制动；所有输入都用离线测试节点产生。
3. 现场实车阶段不发布正/负速度测试消息；即使 ECU 消息只是 ROS 话题，也不把它连接到实际底盘驱动。

通过条件：零速看门狗连续稳定，控制权不会从泊车静默回退到导航，且无底盘/CAN 节点运行。

### 5. 静止定位与导航

1. 车辆保持静止，先运行实际地图服务器和重定位节点，使用已恢复地图；发布初始位姿并验证 fitness、TF `map->odom` 和点云帧。
2. 再启动 LIO-SAM 的传感器链，但不连接控制输出；观察去畸变点云、特征点和里程计是否连续、时间戳是否单调。
3. 运行 Nav2 只做规划服务和 action 取消测试，`cmd_vel` 必须重映射到隔离话题并由订阅器记录，不得连到底盘。
4. 静止阶段全部通过后，才能制定“低速人工看护运动测试”单独方案；该方案必须重新确认急停、限速、通信丢失停车和人员位置。
