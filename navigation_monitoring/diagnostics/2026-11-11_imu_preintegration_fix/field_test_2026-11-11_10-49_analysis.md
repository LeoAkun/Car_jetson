# 2026-11-11 10:49 实车启动失败分析

## 结论

`IMU preintegration is not ready` 是最终健康判定，不是最初触发原因。本轮预积分曾在
10:55:00.365923 进入 ready，随后实际收到两个 0.232 s 和 0.287 s 的 IMU header
间隔，按 `imuMaxGapSec=0.2` 执行重同步并发布 ready=false。没有 GTSAM
Indeterminant、fatal 或预积分进程自行退出。

第二次重同步后约 0.486 s，进程管理器把连续 not-ready 判为永久故障并关闭 LIO-SAM。
这个窗口不足以可靠完成重新初始化和三次成功优化。

## 触发层

- 录包全程 49523 帧、平均约 99.94 Hz，但存在 4 个 header 间隔大于 0.2 s；平均频率
  不能代表启动瞬间连续性。
- 关键两次间隔发生在 Nav2 启动期间：0.231686 s 和 0.286998 s。
- 测试时 PID 37974 仍运行安装文件被替换前的旧 ELF；运行 SHA256 与当前安装版本不同，
  `/proc/37974/exe` 带 `(deleted)`。因此本轮没有运行新的设备时间戳和完整串口帧读取逻辑。
- 间隔呈现“消息到达暂停、一个旧 header 消息延迟到达、随后新 header 消息成簇到达”的
  模式。它与主机调度/启动负载或驱动发布停顿相符，但现有证据不能在主机调度、串口丢帧、
  USB和设备输出之间给出唯一根因。
- 10:55:02.337 的 AHRS CRC 错误和巨大有限四元数是独立的数据完整性证据；它发生在两次
  gap之后，不能解释为两次gap的唯一原因，也未参与当前六轴预积分计算。

## 放大层

1. 进程管理器配置写的是每 1 s 健康检查、连续 3 次失败，但 Nav2 启动等待循环每 0.25 s
   调用 `_tracked_liosam_failure_reason()`，该函数也会修改同一个失败计数。因此实际宽限可能
   小于 1 s，而不是预期的约 3 s。
2. 第二次gap到故障只有约0.486 s；ready要求重置后重新初始化并完成三次成功优化，时间余量
   过小。
3. `resetPreintegrationState(true)` 清理 `imuQueOpt/imuQueImu`，但没有清理
   `pendingOdometry_`。10:55:02.736 日志仍在处理时间戳10:55:01.265的旧修正，说明重置后的
   工作线程在追赶旧校正，进一步延迟恢复。
4. LIO-SAM由进程管理器发送终止信号退出；本轮不能据此判断节点自身无法恢复。室内合成测试
   已证明在没有管理器过早清理且没有旧校正积压时，ready可以 `true -> false -> true`。

## 修复顺序建议

1. 下一轮实车测试前让当前安装的新IMU驱动真正生效，验证设备时间戳是否把主机调度停顿与
   真实传感器丢帧区分开；不应使用本轮旧ELF结果继续调设备时间阈值。
2. 进程管理器对运行中短暂 ready=false 使用基于持续时间的恢复宽限；Nav2等待轮询只能观察，
   不能以4 Hz重复累加健康失败。进程退出和已确认fatal仍可立即失败。
3. 预积分重同步时丢弃重置时刻以前的 pending odometry，保证新epoch从同一时间线的IMU和校正
   开始。
4. 新驱动实车验证后再决定 `imuMaxGapSec`。若设备时间也确认存在0.2--0.3 s真实缺帧，直接把
   阈值关闭并把大dt作为单帧积分并不安全，应保留重同步并让上层等待恢复。
