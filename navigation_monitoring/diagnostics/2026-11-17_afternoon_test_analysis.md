# 2026-11-17 下午实车测试分析

## 结论先行

今天下午不是一个单一故障，而是三条故障链叠加：

1. **地图切换失败的直接原因是 map2 的 Nav2 组合节点没有加载成功。** map1→map2 的重定位已经成功发布了 `map→odom`，失败发生在随后加载 Nav2 composable nodes 的阶段。`load_node` 服务两次超时，最终只留下空的 `component_container_isolated`、RViz 和 costmap cloud，管理器等到 150 秒后才报缺少 Nav2 节点。
2. **重定位反复失败的最高概率原因是多个同名重定位服务实例同时存在。** 旧的 map2 `pcl_localization` 实例从地图切换时缓存了第一帧点云，后续失败任务的全部 PSO 请求又落到了这个旧实例；新的实例虽然被拉起，但没有收到请求。这样搜索的是旧实例的缓存点云，fitness 远高于接受阈值，进程最后正常退出而被管理器误报为“code 0 健康故障”。
3. **行驶中的“停一下、连续倒退、再继续”主要是 Nav2 恢复树的预期动作被反复触发。** 控制器/规划器因起点落入 lethal space、MPPI 无法优化、TF 时间外推失败而中止，行为树随后执行等待 5 秒和 `BackUp 0.30 m @ 0.24 m/s`。底盘状态显示确实切到 R 挡并有实际速度，因此这些倒退不是溜车。

录包中没有证据显示传感器在下午整体关闭；IMU、合并雷达和过滤雷达持续有数据。录包在 16:15:26–16:17:41、16:40:44–16:43:18 有缓存丢失，后一时段正好覆盖最后一次任务失败，应把逐帧数量视为下限。

## 一、地图切换为什么失败

### 1. 重定位不是切换失败点

15:56:14.094 收到 map1→map2 切换请求；旧栈关闭完成后启动 map2 重定位。15:56:43.328 已看到 `map→odom`，平移为 `(-39.30,-5.70)`。因此地图文件读取、点云服务、PSO 输出和 TF 发布都完成了，不能把这次失败归类为“重定位没成功”。

### 2. Nav2 组合节点加载失败

Nav2 日志只有以下有效启动过程：

- `component_container_isolated` PID 45627 启动；
- RViz 因 X11 转发失败退出；这在成功运行中也出现，不是主因；
- 15:56:49.137 和 15:56:49.327 两次出现 `failed to send response to /nav2_container/_container/load_node (timeout)`；
- 没有成功加载 `controller_server`、`planner_server`、`bt_navigator`、两个 lifecycle manager 等组件。

管理器的启动健康检查配置为 150 秒，而地图切换控制器调用 `start_process(navigation2)` 只等待 75 秒。于是：

1. 地图切换控制器在 15:58:02 先判定 Nav2 启动超时，清理调用又连续等待，15:58:17 才发布地图切换失败；
2. 进程管理器仍在阻塞等待，直到 15:59:17 才报“缺少 Nav2 节点”；
3. 导航管理器已经开始发起清理和恢复请求，但这些请求排在阻塞的启动回调后面，连续出现服务等待超时；
4. 旧启动回调结束后，队列中的新启动/关闭请求才陆续执行，造成栈的时序交错。

### 3. 清理逻辑会留下旧进程并制造后续竞争

进程管理器在 `shutdown_process()` 中向进程组发送 SIGTERM 后，只等待根 launch 进程退出；根进程一旦退出就把该名字从 `self.processes` 删除，没有再次核对同一 PGID 下的所有子进程。启动同名进程时也直接覆盖 `self.processes[name]`，没有拒绝重复实例或保存 generation/PID 关系。

本轮结束后仍能看到 PPID=1 的残留：

- 15:56 的旧 map2 `pcl_localization`；
- 15:56 的旧 Nav2 container；
- 16:28、16:31 的两组 map2 重定位；
- 16:33 的 Nav2 container。

这说明“管理器记录为已关闭”和“ROS/DDS 图中已无实例”不是同一件事。切换阶段的 `load_node` 超时最可能由旧组件/服务端点和阻塞式服务调用共同触发；监测快照没有显示内存耗尽，15:56 阶段 CPU 中位数约 38.6%、峰值约 57.8%，内存仍约 22.9 GB 可用，因此没有证据支持“工控机资源耗尽”是直接原因。

### 4. 切换位姿被上游生成，却没有被控制器使用

导航管理器会把切换后的 `switch_pose` 写入 `MapSwitchTrigger`，包含 map2 的 `next_x/next_y/next_yaw`。但 `map_switch_controller` 回调只把 `current_map` 和 `next_map` 传给 `execute_map_switch()`，启动新栈时没有把这个位姿交给重定位。切换因此仍依赖 GPS + PSO，而不是使用已知的跨图初始位姿。这不是 15:56 Nav2 load timeout 的直接原因，却是地图切换后重定位易失败的设计缺口。

## 二、重定位为什么容易失败

### 1. 最强证据：请求被旧服务实例处理

`pcl_localization` 的实现第一次服务调用后把点云放进 `first_cloud_`，后续调用一直复用该缓存。今天下午同一 `/re_localization` 服务名下同时存在多个 `pcl_localization`，服务客户端没有绑定特定 PID。

按各进程日志统计的服务调用数如下（一次 PSO/爬山候选位姿对应一次服务调用）：

| 阶段 | 旧实例 `pcl_localization_node_45421`（15:56 启动） | 本次新实例 | 结果 |
|---|---:|---:|---|
| 16:02 失败搜索 | 3312 | 16:02 新实例无请求日志 | 全部候选都用旧实例在切换点缓存的点云；最终 fitness `0.3018` |
| 16:10 成功搜索 | 213 | 新实例 175 | 请求在实例间分配，恰有实例给出 `0.0298` |
| 16:19 失败搜索 | 3312 | 16:19 新实例无请求日志 | 再次全部落到旧实例；最终 fitness `0.3823` |
| 16:28 成功搜索 | 108 | 新实例 52 | 混合实例，出现 `0.0102` |
| 16:32 成功搜索 | 203 | 三个新/旧实例合计 596 | 混合实例，出现 `0.0103` |

失败搜索的最终分数分别是 `0.3018` 和 `0.3823`，接受阈值是 `0.05`，不是阈值边缘抖动，而是完全没有在正确点云上找到匹配。旧实例缓存的是 15:56 切换时的第一帧点云；之后车辆位置变化后，继续用它处理新位置的 PSO 请求，足以解释“有时成功、有时完全失败”的不确定性。

### 2. 搜索本身也比较脆弱

当前 `nav2_init_pose`：

- 以 GPS 转换点为中心，只搜索 ±10 m 方框；
- PSO 角度步长 30°；
- 30 个粒子、6 轮迭代，再做局部爬山；
- 一次失败搜索需要 6～8 分钟；
- fitness 达不到 0.05 时返回 `False`，但 Python 主程序正常退出 code 0。

GPS 种子偏差超过 10 m、现场几何特征不足、当前点云被障碍遮挡，都会让搜索落在错误区域。尤其是跨图切换已有 `switch_pose` 时仍完全依赖 GPS，放大了这个风险。建议先消除重复服务实例，再验证搜索半径和阈值；单独放宽阈值会把错误位姿送进导航，不能作为首要修复。

### 3. “code 0”不是重定位成功

重定位失败时 `execute_logic()` 返回 False，`main()` 最终正常退出；进程管理器只能看到“launch process exited with code 0”，无法知道是 fitness 不达标。故障消息应该带上最终 fitness、候选坐标、服务实例标识，并用明确的失败结果或非零退出码区分“搜索完成但未通过”和“进程崩溃”。

## 三、行驶中为什么会停、倒退几次、再继续

### 1. 行为树明确配置了这种恢复动作

导航行为树的恢复轮询顺序是：

1. 清空局部/全局代价地图；
2. 等待 5 秒；
3. `BackUp backup_dist="0.30" backup_speed="0.24"`；
4. 重新规划和继续跟踪。

外层 `RecoveryNode` 允许最多 10 次重试。因此一次局部规划问题不会立刻结束任务，而是表现为“停住—倒退—再规划—继续”，连续几轮就会看到多次倒退。

### 2. 录包确认是实际 R 挡倒车

`/cmd_vel_nav` 在多个段连续输出负的 `linear.x`，`/cmd_vel` 也同步出现负速度；`/vehicle_status` 同时显示 `shift_level=3`（R 挡），`cur_speed` 非零，随后又回到 D 挡继续前进。典型恢复段：

- 16:14:23–16:14:49：多次倒车恢复；
- 16:15:14–16:15:49：连续倒车与重规划；
- 16:16:14、16:16:22、16:16:30 附近：短倒车恢复；
- 16:17:31–16:17:45：连续三段负速度；
- 16:34:15–16:35:34：多次倒车并恢复行驶；
- 16:38:39–16:39:15：倒车恢复；
- 16:41:10、16:41:17、16:41:35、16:41:43、16:41:51–16:41:58、16:42:15：多次恢复。

固定约 `-0.24 m/s` 的短段最符合 BT `BackUp`；幅值约 `-0.3～-0.56 m/s` 的较长段也可能是 Smac REEDS_SHEPP 允许的规划倒车，因为参数中 `vx_min=-0.5556` 且运动模型为 `REEDS_SHEPP`。两类倒车都不是人工控制命令。

### 3. 触发恢复的现场原因

有效行驶的 Nav2 日志反复出现：

- `Optimizer fail to compute path`；
- `Starting point in lethal space! Cannot create feasible plan`；
- 多次 `global_costmap/clear_entirely_global_costmap` 服务超时；
- 16:33 任务还反复出现 `Lookup would require extrapolation into the future` 和 `Unable to transform robot pose into global plan's frame`。

其中 `Starting point in lethal space` 说明当前定位点或其足迹在全局代价地图中被判为致命格；这会让规划器无法从当前位置生成路径。16:11、16:33 两个有效行驶阶段分别出现大量控制器 30 Hz 周期超时、优化失败和 lethal-space 规划失败，正好对应录包里的多次停顿/倒车。

### 4. 清图服务超时会放大循环

`nav2_real_params.yaml` 设置 `default_server_timeout: 30`，Nav2 代码把它解释为 **30 ms**。日志中的清图服务超时与这个数量级一致；清图尚未完成，行为树就进入下一轮恢复，于是重复等待和倒退。这个参数应按实际服务耗时重新设定并验证，而不是只依赖反复 BackUp。

### 5. 负载和录包是放大因素，不是最初根因

16:10–16:18 阶段监测到 CPU 峰值约 68%、负载峰值约 18.8；16:32–16:43 阶段 CPU 峰值约 94.5%、负载峰值约 21.4，录包缓存丢失集中在 16:40:44–16:43:18。高负载会加剧控制循环和 TF 时序问题，但 16:11 阶段已经在资源尚未到峰值时出现 lethal-space 和 optimizer 失败，所以不能把所有停顿归因于录包 I/O。

## 四、关于“位置跳变”的判断

按 TF 的消息头时间排序后，明显的大幅 `map→odom` 变化集中在重定位/换图开始时：15:53:40、15:56:43、16:11:23、16:29:03。这些是重新建立地图坐标系的初始化跳变，不是已经稳定行驶后的连续跳变。

16:33 之后主要证据是 3～23 ms 的 TF 未来外推错误，而不是几十米的位置瞬移。录包数据库在缓存拥塞时的写入时间与消息头时间可相差约 10 秒，不能把这个记录器延迟直接解释为车上 TF 延迟。

## 五、修复优先级

### P0：测试前必须解决

1. **一次只允许一个重定位服务、一个 Nav2 容器、一个 LIO-SAM 栈。** 启动前按命令行/PGID/ROS 服务名三重检查；同名服务已存在时拒绝启动，而不是覆盖字典句柄。
2. **关闭时验证整个进程组和 DDS 实例。** SIGTERM 后检查 PGID 下每个成员，超时再 SIGKILL；只有确认成员全部消失后才删除管理器记录。
3. **把进程管理器改成非阻塞状态机或可重入服务。** 当前 MultiThreadedExecutor 下服务没有显式 ReentrantCallbackGroup，长时间 `wait_for_process_healthy()` 会堵住清理和状态查询。启动调用方与管理器统一同一个超时，并让 map switch 在任务级别等待最终结果。
4. **修复 map switch 的异常回滚。** Nav2 load timeout 后要取消当前 generation、清理全部子进程，再允许下一次启动；不能让恢复请求排队到旧启动回调结束。

### P1：定位与地图切换

1. 把 `switch_pose` 真正传入 map2 的初始化，优先用跨图已知位姿，GPS 只作为校验或扩大搜索的备用种子。
2. 把重定位结果做成明确的 action/service result，至少返回 `fitness、x、y、yaw、server_pid/generation`；fitness 不达标时不要正常 code 0 退出。
3. 在所有候选请求中记录服务端实例，测试时确认一轮 PSO 的请求只由当前实例处理。
4. 在导航管理器接收任务时校验相邻航点地图名变化：地图名变化必须经过 type=4 切换点，否则直接拒绝任务并说明缺少切换点。

### P1：规划与恢复

1. 先解决 `default_server_timeout=30 ms` 与清图实际耗时不匹配的问题，再评估清图服务是否真正完成。
2. 对 `Starting point in lethal space` 记录触发时的 map/odom 位姿、足迹轮廓、全局/局部代价地图窗口和清图前后状态，区分自车近场回波、定位误差和真实障碍物。
3. 限制同一故障事件的 BackUp 次数，并在没有位姿/代价地图进展时结束任务交给人工处理；不要让 10 次恢复在同一格子里循环。
4. 对 16:33 出现的 TF 外推错误检查发布频率、时间源和消息时间戳，避免在 TF 未覆盖目标时间时继续调用控制器。
